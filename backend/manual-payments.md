# 微信经营收款码与人民币钱包

普通用户从 Wormhole AI 首页“注册”（`/register`）创建账号，账号和 API Key 是两层身份。登录后的工作台可以创建、撤销本人的 Key，查看可用模型、充值、订单和调用扣费。同一账号下所有 Key 共用人民币钱包。首次注册用用户名和密码，无需短信或邮箱服务。恢复码只在注册或重置成功时展示，使用后随即轮换，并撤销该账号已有会话及 Key。

所有账号都从首页“登录”（`/login`）使用用户名和密码登录。服务端校验身份后，普通用户进入 `/account`，管理员进入 `/console`。在“用户管理”可查看注册用户和余额、停用或恢复账号；停用会注销该用户会话并立即停止其 Key 的后续调用。在“模型映射”中选定有人民币价格的型号并勾选“向注册用户开放”。已有内部模型默认仅内部可用。普通用户无权修改供应商、模型配置、价格或其他用户的账本。

管理员在“渠道”中填写模型分组。一个渠道属于一个分组，模型别名按其已启用且已配置的主备渠道出现在相应分组。用户可在工作台浏览这些分组，创建 Key 时选择其中一组。该 Key 的模型列表、调用与故障切换都限制在所选组内；同一账号下各组仍共用钱包。旧渠道和旧用户 Key 使用 `default`（默认分组）。内部业务 Key 沿用原有授权。

历史业务 Key 仍可从“业务 Key 充值”（`/wallet`）独立使用。对于管理员签发的 service Key，在“API Keys → 编辑”勾选“使用人民币预付余额”后才从该独立钱包扣款。旧 Key 不会因注册了同名账号而被自动归属，Key 轮换保留原钱包。

## 微信经营码与核款

在管理后台「收款管理 → 微信支付」上传微信经营收款码 PNG/JPG（最多 4 MB），核对预览后启用。也可通过 AI_GW_WECHAT_QR_FILE 提供启动时收款码。上传的图片优先。生产部署使用 HTTPS。

用户点击「微信扫码充值」生成待入账订单，网站不要求填写金额。微信扫码后按收款页面付款；备注可用时填写网站订单号，否则把网站订单号和微信支付单号一同发给收款人。核款人按商户账单确认订单归属、交易单号和实收金额后，在「收款管理」提交入账。系统记录人民币实收金额，交易单号唯一，重复确认不重复加余额。历史固定金额订单仍核对原金额；历史支付宝订单在「支付宝历史订单」处理。

在后台「收款管理」选择收款渠道，展开「用 iPhone 快捷指令核款」，复制 HTTPS 核款地址并下载对应指令。微信使用 `AI_GW_WECHAT_RECEIPT_TOKEN`，历史支付宝订单使用 `AI_GW_ALIPAY_RECEIPT_TOKEN`；两者应独立生成，至少 32 字符。新指令导入时填写地址和本渠道凭证本身，无需输入 `Bearer`。

先在商户账单核实到账，再填写网站 12 位订单号、账单实收金额（元）和完整平台交易号；备注没有订单号时，向付款人索取网站订单号。提交后手机显示入账结果，重试同一笔已入账交易不会再次加余额。旧指令的接口与 JSON 返回保持兼容，正在使用的指令可重新下载并导入以获取新提示。

普通用户的完整 Key 加密后存储，列表仅返回预览。用户可登录后复制自己的 Key 或直接导入 CC Switch。旧 Key 仅保存过摘要，需要明确更换后才能使用这些操作。部署时通过 AI_GW_USER_KEY_SECRET 提供长期稳定的共享加密密钥，或持续保存钱包数据文件旁的 .key 文件。更换或丢失加密密钥会影响已有 Key 的复制和导入。

## 人民币计费

收款和钱包使用人民币一比一入账。这里购买的是余额，不产生包月、周重置或美元额度。用户可在钱包看到最近 30 笔订单及 20 笔调用；持久化账本保存完整记录。

调用价格使用当日 [CodexZH 模型页](https://codexzh.com/models) 的“套餐折扣后”人民币标价快照。按对外模型别名匹配，别名未列入时使用主路由的上游型号；故障切换沿用最初报价。预付费模式只放行已有价格的模型。每百万 Token 分普通输入、缓存读取、缓存写入和输出价。设有长上下文档位的模型在输入超过 272000 Token 时按长档计算整笔；图像按每次成功生成请求计费，一个响应即使包含多张图也只扣一次。服务端以 10 位人民币小数的整数记账，避免小额调用按分舍入。

预付费请求在转发前校验余额。Token 接口以请求正文和格式开销保守估算输入，再加输出上限（默认 4,096 Token，单次总上限 32,768 Token）；图像请求按当前单次售价校验。余额不足时返回 `402`，不会调用上游。可缩短输入、调小输出上限或先充值。Token 计费暂不支持无法预估的图片、音频、文件输入或上游托管工具；本地函数工具仍可用。该校验是预估，不代替上游实际用量，且依赖上游遵守输出参数。

每个钱包同时结算一笔请求（注册用户的多个 Key 共享此限制）；开始时记录当时余额作为最高可扣金额。调用中途充值也不会提高该次扣款上限，超额部分由网关承担。上游调用前失败或上游直接返回错误状态扣零。流式及非流式结果使用上游报告的用量；开始交付后缺少可信用量、未取得图片数量、未定义的缓存写价等进入待核对，暂停该钱包的后续付费调用。其他账户不受影响。请求进程崩溃后，超过本次路由超时时间和安全余量的未结记录也可核对。

管理员可在管理后台“计费 → 待核对的人民币扣费”中填写实核金额、核对依据并确认结算。使用接口时，可带现有管理凭证请求 `GET /admin/payments/reviews` 找到调用编号、型号和可用证据，再通过 `POST /admin/payments/reviews` 提交 `{"id":"调用编号","amount":"0.00","reason":"已核实供应商未产生费用"}`。金额以人民币元为单位、最多 10 位小数；仅在核对后填写确切费用或决定免收。操作会写入审计日志。快捷指令的收款凭证不能执行此操作。

## 回归检查

`node backend/test-wallet.mjs` 在临时目录建立 SQLite 账本和模拟上游，核对同额订单、重复提交、错额、权限、余额不足、流式计价、人工核对以及重启恢复。不会向支付宝发起付款。
